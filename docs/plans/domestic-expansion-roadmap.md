# 国内拡張ロードマップ（D系）

更新日: 2026-09-14。状態: **D0調査完了、代替候補調査済み。D1以降は候補見直し中**。

## 背景と位置づけ

`docs/plans/cross-border-research-roadmap.md`（越境EC, X系）の検討の結果、2025年の関税制度変更（米国de minimis撤廃等）と越境プラットフォーム手数料により、海外販売を前提とした価格差モデルは採算が悪化していると判断した。一方、日本国内で完結する価格差検出は、関税・為替リスクがなく、既存のCore契約（ADR 0003）をそのまま転用できるため、投資対効果が高い。

当初の第2市場候補はメルカリだったが、D0調査（下記）の結果、メルカリは規約・技術構造の両面で自動取得が不可と判定された。代替候補調査（[D0b](d0-second-market-candidates.md)）により、楽天ラクマも同水準の理由で対象外、PayPayフリマが規約面での新規リスクなし（既存Yahooオークション実装と同一のLINEヤフー共通規約）の有力候補として浮上している。技術構造（静的HTML取得の可否）の確認はまだ残っている。

本ロードマップはX系より優先度を上げる。X系（越境）はX0（調査）のみ独立して継続してよいが、A0-Required完了をX1着手条件とする既存方針は維持する。

## 前提として維持する制約

- 自動入札・自動出品・自動再出品は行わない（技術的にも意図的にも対象外）。人間が最終判断・実行する意思決定支援ツールという位置づけを維持する。
- ヤフオク・メルカリいずれの規約も自動化ツールを禁止しているため、取得は分析目的の範囲に留め、既存のYahoo取得と同水準のリスクを超えない。
- 中古品の仕入れ・転売を事業として継続する場合は古物商許可が法的に必要（本ロードマップの対象外、利用者側の対応事項）。D6（古物台帳機能）はこの許可取得後を前提とする。

## フェーズ

### D0: メルカリ取得可能性・用途調査

越境ロードマップのX0と同じ形式で、メルカリの取得経路・利用規約上の許容範囲・データ品質（画像・状態・価格種別）を確認する。証拠URL・確認日を記録する。

- **開始条件:** なし、今すぐ着手可能。
- **完了条件:** 利用可/限定可/不明/不可を判定し、根拠を記録する。
- **状態: 調査完了（2026-09-14）。判定は「限定可（自動取得は不可、手入力のみ）」。** 詳細は[D0調査記録](d0-mercari-research.md)。利用規約ガイドが「弊社が提供するインターフェイスとは別の手法を用いてサービスにアクセスすること」「商業目的での無許可利用」「リバースエンジニアリングによる複製・二次利用」を明示的に禁止しており、加えて検索結果画面がJavaScriptレンダリングのSPAで既存Yahoo実装と同水準の取得方式（静的HTML取得）が技術的に使えないことを確認した。メルカリを対象としたD1（Mercari Provider実装）は着手しない。手入力での代替（D1'）は、転記情報の保存・表示が規約上の権利条項との関係で未整理であることと、そもそも「人より速く判断する」という目的に対して手入力では速度の優位性が生まれないことから、採用しない。

### D0b: 代替候補調査（実施済み）

メルカリが不可判定となったため、楽天ラクマ・PayPayフリマを同じ形式で調査した。

- **状態: 調査完了（2026-09-14）。** 詳細は[D0b調査記録](d0-second-market-candidates.md)。楽天ラクマはメルカリと同水準の明示的禁止があり対象外。**PayPayフリマは規約面で新規リスクを生まない**（既存Yahooオークション実装と同一のLINEヤフー共通規約に拘束される）ため有力候補だが、検索結果ページが静的HTMLでデータを返すか技術未確認であり、これがD1着手可否の分岐点になる。

### D1: PayPayフリマ Provider実装（候補、技術検証待ち）

ADR 0005のCore契約（Marketplace/Product/MarketListing/PriceObservation）を維持しつつ、対象marketplaceを`mercari_jp`から`paypay_frima`へ差し替える。[ADR 0005](../decisions/0005-domestic-second-marketplace.md)を参照。

- **開始条件:** `https://paypayfleamarket.yahoo.co.jp/search?keyword=...`への単発HTTP GETで実データが静的HTML内に含まれることを確認すること（D0bで未実施）。含まれない場合は本フェーズ全体を見送る。
- **完了条件:** fixtureベースの取得・パースがYahoo実装と同水準で検証される。

### D2: 価格差検出MVP

[Domestic Cross-Market](../features/domestic-cross-market.md)に従い、ターゲット分析へメルカリ比較を追加する。

- **開始条件:** D1完了。
- **完了条件:** 同一キーワードで両市場の中央値・差額・根拠件数が表示され、所有者スコープ・CSRFが既存パターンで検証される。

### D3: 発見型スキャン

[Opportunity Discovery](../features/opportunity-discovery.md)に従い、監視カテゴリ単位での新着スキャンを追加する。

- **開始条件:** D2完了（比較ロジックを流用するため）。
- **完了条件:** 初回全件通知にならないこと、監視カテゴリごとの負荷上限が確認されること。

### D4: 商品画像の取得・表示

[Listing Images](../features/listing-images.md)のPhase Aを実装する。D1〜D3と独立して着手可能。

- **開始条件:** なし、今すぐ着手可能（Mercari接続を待たない）。
- **完了条件:** 相場検索・ターゲット分析・在庫・出品管理・通知の各画面でサムネイルが表示され、画像なし/失効時もUIが崩れない。

### D5: 実績フィードバックループ（Phase 7B前倒し）

既存の`docs/plans/release-feature-roadmap.md` Phase 7Bを前倒しする。確定済み`SaleRecord`データを使い、キーワード・カテゴリ別の実現利益を可視化し、利用者自身のニッチ発見を支援する。

- **開始条件:** `SaleRecord`データが一定件数蓄積していること（件数閾値は着手時に決定）。
- **完了条件:** キーワード・カテゴリ別の確定利益ランキングが表示される。

### D6: 古物台帳エクスポート

古物商許可取得後を見据え、`InventoryItem`/`SellerListing`/`SaleRecord`から古物営業法が求める記録項目（取引年月日・品目・数量・特徴・相手方情報等）を満たすエクスポート機能を追加する。

- **開始条件:** 利用者が古物商許可を取得済みであること。
- **完了条件:** 法定記録項目を満たす形式でエクスポートできる。

## 推奨順序

D0・D0bの調査は完了した。D4（画像）は依存関係がなく、現時点で最も着手しやすい実装単位である。D1（PayPayフリマ）は技術検証（静的HTML確認）が先決で、それが通らなければD2・D3もそのままでは着手できない（対象市場を持たないため）。D5はSaleRecordの蓄積を待つ。D6は許可取得後でよい。

**現時点の推奨: D4を先に実装しつつ、D1着手可否を決める技術検証（1回のHTTP GET確認）を並行して行う。**
