# 越境EC価格差リサーチ ロードマップ

更新日: 2026-09-12。状態: **A0追加の計画改訂済み・A0/CrossBorder機能未実装**。

## 目的と採用方針

国内で仕入れ、海外で販売する候補について「同じ商品か」「比較価格の根拠は何か」「費用を引いて利益が残るか」を確認し、購入判断と在庫登録へつなげる。

Systema内に独立した越境リサーチ領域を追加する。共通ログイン・画面・既存在庫を活用し、外貨計算・商品照合・市場別取得は境界を分ける。初期は同一リポジトリ・同一PostgreSQLを使う。別Djangoアプリを第一候補とし、具体的な配置と連携契約はX1のADRで確定する。アプリ・テーブル・APIが既に存在することを意味しない。

初期利用者はログイン済みの国内仕入れ・海外販売者。国内1市場、海外1市場、配送先1か国、限定1カテゴリから開始する。国内候補はYahoo、海外調査候補はeBayとするが、採用はX0の取得・用途検証で決める。対象カテゴリは型番・版・状態を照合しやすく、配送条件と根拠データを確保できるものから選ぶ。

## 現状と既存ロードマップとの関係

- 基準コミット: `9411de2`。既存資料には在庫・購入上限・通知・販売実績・監視の実装記録がある。今回これらの稼働・CIを再検証していない。
- 作業ツリーにはPhase 9の未追跡ファイルがある。ファイルの存在は統合済み・検証済みの証拠ではない。公開準備の実装差分と資料の整合確認をP0に残す。
- 既存のM0〜M4は維持する。M3は「海外仕入れ→国内販売」、本計画のX系は「国内仕入れ→海外販売」。配送方向、販売市場、手数料、税負担の前提を混同しない。
- X0はM0の取得調査を再利用し、X1はM1と市場識別・金額・観測の契約を共有する。M2のメルカリ対応やM3の輸入対応はX系の前提にしない。
- Phase 9の公開準備とX0の調査は並行可能。外部取得が未確定でもYahoo単独版の公開準備を止めない。
- 検索履歴比較、Phase 7Bの高度推薦、メール通知は既存の保留条件を維持し、越境MVPの完了条件へ追加しない。

## A0 — Systema Core Stabilization / Architecture Consolidation

### 目的・必要性・対象外

Yahooで実証できる最小の境界を整備し、2〜3市場へ拡張できるModular Monolithにする。新機能が既存のHTTP依存や不完全な保存処理を再利用して負債を増やす前に、Web/CLI共通ユースケースとデータの意味を固定する。全面リライトや全legacy排除は完了条件にしない。

対象は検索実行・保存・所有者・Yahoo取得・金額/出品/観測の契約と、その回帰検証。今回の編集は計画のみ。eBay/Mercari/Surugaya実装、AI照合、Celery/Redis導入、React移行、マイクロサービス、API削除、破壊的migration、大規模移動は対象外。Product等の物理テーブルをすべてA0で作る必要もない。

これらは責務区分であり、直ちにDjangoアプリ分割を行う指示ではない。

### 保存・migration・rollback

1. A0.1〜4は既存テーブルのまま移行する。取得と解析はtransaction外。保存単位は1検索runとその商品行。失敗時は商品行/成功runをrollbackし、失敗記録を別に残す。保持期限による削除は保存成功後に行い、失敗した更新で過去の成功履歴を削除しない。通知/watch更新は成功した保存結果に基づき、再実行キーで重複を防ぐ。
2. bulk_createは検証やsave/signalを自動代替しないため、対象モデル/receiverの有無を確認してから採用。閉札/現在の片方だけ失敗したtarget検索は、成功したrunを保持し、従来のHTTPエラー契約と新しい内部部分失敗状態を区別する。
3. 新モデルの物理導入はX1で確定後、追加テーブル/nullable参照→再実行可能な分割backfill→件数/金額/所有者/重複検算→限定読取切替の順。既存のapp label・db_table・PK/FK・JPY列を改名/削除しない。A0中の全件backfillは不要。
4. SearchDayは現在保存時のnaive文字列。元の文字列を残し、既知のタイムゾーンを証明できる場合のみ変換。不明・不正値は隔離/不明として扱う。Biddingは整数変換可否を記録し、欠損を0へ捏造しない。ownerless行は新たに公開せず所有者不明として保持する。
5. 互換期間は旧endpoint/分析/履歴の読取が残る間。legacy scrapingの廃止検討は、全reader移行・保持条件・検算・復元リハーサル・利用実績の確認後。日付だけで廃止しない。dual-writeが必要なら同一DBの原子保存と照合を限定期間だけ行う。
6. コードは小単位で旧窓口へ戻せるようにする。新テーブルは残して読取切替を戻し、DROPをrollbackの既定にしない。旧契約で表現不能な外貨データは新領域を停止して保持する。実データ復元は隔離環境で事前リハーサルし、追加データの消失を伴う操作は別承認とする。

### テスト・CI・文書更新

- A0.0でlegacyと移行後のHTTP status/JSON型・項目・所有者・GET副作用を固定。v1へ一括統一せず、旧adapterと新APIが同一UseCaseを使う。入力解析だけでなく戻り値と失敗の変換もViewに置く。
- domain/DTOはDB・HTTPなし、UseCaseはfake Provider/Repository、YahooはHTML fixture、RepositoryはPostgreSQLで原子性/同時実行/再送を検証。SQLite互換も対象。CIで大量ライブ取得を行わない。
- Web/CLIの条件同一性、匿名からログインへの引継ぎ、他人のID、保存途中例外、件数一致、二重通知、保持処理、欠損/通貨丸めを重点検証。UI非変更でも移行した検索・watch動線のE2Eを行う。
- 既存`verify --feature market-search`等を起点に単位ごとの関連テストを追加。新パスをverifyのルーティングへ登録し、A0の対象UseCase/DTO/Repositoryがmypy対象に入ることを確認。A0完了時のfullは1回、CIでは既存PostgreSQL/SQLite E2E/Sphinxジョブを維持する。
- coverage最低35%を引き上げること自体を目標にしない。失敗/境界分岐の検証を優先。新しいappがMain外にできる時はmypy/coverage対象を明示追加する。
- A0.5/6で`docs/decisions/`にADR、`docs/design/api.md`に互換写像、`docs/design/database.md`にモデル/移行契約を追加する。A0.1〜4は`docs/architecture.md`と該当feature、試験追加は`docs/testing.md`、進捗は本書に反映する。今回の計画記載を実装済みADRとみなさない。

### CrossBorder開始ゲートと後続負債

**X1開始条件（A0-Requiredの最小完了）**:

- A0.0〜4: 新市場処理をutilsに追加せず使えるProvider/Repository/UseCaseがYahooで動作し、target検索とrun_alertsの双方がHTTP Requestなしで同じUseCaseを呼ぶ。
- A0.2/7: 保存失敗を成功として扱わず、原子性・所有者・再送・旧API互換が関連テストで確認される。
- A0.5/6: Marketplace、Product/Listing/Observation、Money/FX、評価版、legacy移行/保持/戻し方の最低契約が文書化される。全Coreテーブルの実装は不要。
- 対象変更のローカル検証とCI検証が記録され、X0で少なくとも手入力版の範囲・用途が成立する。本番検証はX1の前提ではなく、公開時のP0ゲート。

**X2の実装開始条件**: 上記に加えX1で具体的なAPI/DB・丸め・所有者・fixture・受入例が確定している。設計だけでUseCase分離が終わった扱いにしない。

全旧APIのv1統一、予測/履歴の残りの抽出、全件Product照合、JPY列の全面移行、全watchの評価履歴化、JS共通化、requirements分割、生成物削除は並行/後続でよい。移行対象経路に影響しない整理をゲートに含めない。JSはMain/static/JSにMarketComparison等の共有が既にあり、実際の重複・回帰コストを計測して限定する。

**現在の判定: X1へはまだ進めない。** A0.0〜A0.3はSQLiteでローカル検証済み。A0.4のJob/CLI共通化、A0.5/6の具体契約、A0.7のPostgreSQL/CIを含むゲートが残っている。次はA0.4へ進む。X0は継続可能。

| X1 境界・金額・根拠の設計 | A0の契約に沿うCrossBorder API/DB追加設計、所有者、商品照合、計算例、試験用データ | A0-Required完了かつX0で少なくとも手入力の入力範囲と利用条件が確定 | 既存互換、通貨精度、欠損、保存期限、移行/戻し方、在庫連携窓口を定義。代表例を手計算と照合 | A0待ち |
| X2 手入力MVP | 候補URL・価格・根拠・為替・費用の入力、比較、利益/購入上限、保存 | X1完了 | ログイン所有の候補を作成・比較・修正できる。前提不足は判定不可。単体・所有者/DB・画面検証を通過 | 未着手 |
| X3 1市場ずつの取得接続 | 許可されたデータを手動更新し、出典と鮮度を表示 | X2完了かつ当該市場のX0自動取得ゲート通過 | fixture検証と最小ライブ確認を別記。部分失敗・重複・削除/期限・利用上限を確認。失敗で成功結果を消さない | 未着手 |
| X4 在庫と販売結果への接続 | 採用候補を在庫へ移し、後日の実費・確定売価と比較 | X2完了、既存在庫契約確認。X3は必須でない | 再入力を減らし、二重登録・他人の候補移管を防止。判断時の前提を固定し、外貨販売実績の扱いを追加設計・検証 | 未着手 |
| X5 自動更新と通知 | 保存した候補の定期更新、利益条件に合う変化の通知 | X3完了、同期の判定が安定 | 実行管理・再開・多重実行防止・重複通知防止・停止を検証。本番稼働はP0相当の運用確認とスケジューラー選定後 | 未着手 |
| X6 限定提供・収益性検証 | 少人数で利用し、使われる機能と取得原価を測る | X2完成後に手入力版で開始可能。提供する自動機能は各ゲート通過 | 判断時間・誤比較・継続利用・支払い意思・利用原価から、改善/有料化/保留を決定 | 未着手 |
| X7 拡張・独立の再評価 | 次カテゴリ/市場、法人API、独立製品を比較 | X6で継続需要と原価を確認 | 追加ごとの取得調査と小さな検証で判断。独立には移行・認証・運用費を含む別計画を作る | 保留 |

推奨順は **P0ベースライン確認 → A0-Required → X1 → X2 → X3/X4 → X5**。X0はP0/A0と並行し、Provider・識別子・価格種別・出典・保持条件・利用上限をA0/X1へ返す。X0のAPI待ちでA0全体を止めない。X5はX3が必須で、在庫を対象とする通知のみX4も必須。X6は小さな提供単位ごとに行う。X3の取得権確保が遅れる場合はX4と手入力版X6を先行し、自動取得済みとは表示しない。

## X0: 最初に作る調査成果物

市場ごとに次の台帳を作る。公式資料・契約を確認した事実と推測を分け、本計画作成時点では外部条件を再確認済みとしない。

| 記録項目 | 判断に必要な内容 |
|---|---|
| 取得経路 | 公式API、許可フィード、契約、利用者本人の手入力。APIと対象用途の本番利用条件 |
| 価格の意味 | 出品/入札/販売済み表示/本人の確定売価、成約日時、数量、送料、状態の取得可否 |
| 用途・保持 | 商用表示、派生分析、キャッシュ/履歴の期限、削除要求、通知、CSVの可否 |
| 品質 | 型番・版・地域仕様・付属品の照合可否、欠損率、観測日時、比較できない例 |
| 原価と運用 | 利用上限、想定更新頻度、利用者あたり取得量、費用、障害時の縮退 |
| 結論 | 利用可/限定可/不明/不可、証拠URL、確認日、再確認条件、次の作業 |

既存Yahoo取得の実装は新しい商用用途の許諾証拠ではないため、国内側も確認する。eBayの出品検索を成約履歴とみなさない。成約根拠が確保できなければ「出品価格比較と仮定の利益試算」に用途を限定する。有料契約・対外申請・提供先選定は本計画作成に含まない。

## X1〜X2: MVPの契約

### 入力・出力

- 入力: 国内候補、海外比較対象、型番/版/状態/付属品/数量、配送先、元通貨額、価格種別、観測日時、出典、為替の方向・時点・取得元、費用、目標利益。
- 出力: 比較可否と理由、根拠件数・対象期間、見込み利益、購入上限、前提を変更した試算、不足項目、次の作業。
- 想定売価は参照根拠と利用者の仮定を区別する。検索結果件数を販売率や市場全体の需要としない。高値出品の存在だけで高利益候補と断定しない。
- 必要な送料・為替・配送可否・費用が不明なら、条件付きまたは判定不可とする。未知と0を区別し、推測値に取得済み表示を付けない。
- 空結果、比較対象なし、未対応、古い根拠、部分失敗、取得停止を異なる状態として表示する。

### 計算と所有者

見込み利益は、海外での受取見込額から国内仕入れ、仕入送料、国際配送、梱包、販売/決済費用、売り手負担の税等、返品損失見積を差し引く。購入上限は同じ前提と目標利益から求める。売価・送料受取・税・手数料の計算基準と負担者を分け、二重計上を防ぐ。税率や返品率を一律の事実として固定しない。

元通貨額はDecimalと通貨コードで保持し、換算後の表示額と分離する。為替方向、丸め単位・タイミング、計算バージョンをX1で決める。既存円整数フィールドへ外貨を入れず、設定変更で過去判断を再計算・上書きしない。

保存・比較・通知・在庫連携はログイン所有者に限定する。ユーザーの費用・候補・判断履歴を共有データにしない。外部根拠の削除期限がある場合は元資料や派生値の保持可否を確認し、削除後は根拠参照不可と表示する。監査目的で無条件に永久保存しない。

### 依存方向

画面/APIと収集コマンド → 越境業務サービス → 純粋な商品照合・費用計算。業務サービスは取得/保存の窓口を使い、市場別アダプターが外部I/Oを担う。計算はDjango・HTTP・Yahooパーサーに依存しない。

`Main/views/utils.py`に市場分岐を積み増さない。既存全体の再編や共通ライブラリ化は前提にしない。在庫との連携はサービス境界で所有者と二重登録を検証し、越境領域から既存テーブルを随所で直接更新しない。新領域のAPI配置と既存`Main`境界との関係はADRで明記する。

### 最小受入例

- 同型番でも地域仕様・状態・付属品・枚数が異なる場合、比較対象から除外または要確認になる。
- 送料未入力と送料0、為替未入力、外貨小数、目標利益の境界、赤字を区別できる。
- 401/403等の権限問題、429/一時障害、解析失敗を区別し、失敗を売切れと扱わない。
- 別ユーザーの候補IDでは閲覧・変更・在庫登録できない。再送や同時登録で在庫を二重作成しない。
- 費用/為替の変更後も採用時の判断が確認できる。保存期限を超えた根拠は利用可能と表示しない。

## X3〜X5: 収集と連携

最初は手動更新と小さなページ数から始める。自動化では実行ID、状態、再開位置、取得元ごとの利用枠、timeout、上限付き再試行、重複防止を設ける。市場と外部IDで出品を識別し、所有者・実行・観測単位の保存一意性はX1/X3で定義する。外部通信中はDBトランザクションを保持せず、保存前に所有者/実行状態を確認する。

収集処理はHTTP画面処理を呼ばず、同じコードベースの独立プロセスから業務サービスを呼べる構造にする。キュー製品や常駐サービスは必要量を測って選ぶ。本番の多重実行防止、プロセス強制終了、途中再開、利用枠超過、削除要求を検証してから自動更新を有効にする。

在庫連携は円の国内取得費と判断根拠を渡す。海外販売実績は元通貨、換算日、実費を含む追加契約を設け、Yahoo限定のSellerListing更新や円建てSaleRecordに外貨の意味を押し込まない。海外自動出品は含めない。

通知は「目標利益条件を満たす」「補完すべき費用がある」など判断に結びつける。初回全件通知、取得失敗による消失通知、同じ観測の重複通知を防ぐ。通知から根拠と前提へ戻れることを完了条件とする。

## X6〜X7: 利用検証と収益化

初期の検証目安は3〜5人・2週間を提案する。募集・提供開始の確約ではなく、開始前に参加者と測定方法を決める。

| 指標 | 測り方・次の判断 |
|---|---|
| 判断時間 | 同種の候補を従来手順とMVPで比較し、短縮と判断根拠の欠落を確認 |
| 誤比較 | 手確認した比較ペアの不一致率と原因を記録。高利益に見せる重大な誤照合を優先修正 |
| 再入力 | 候補から在庫登録までの再入力項目数を比較 |
| 継続利用 | 翌週も実際の仕入れ検討で使われたか確認 |
| 原価・支払い意思 | 利用者別取得回数、インフラ/データ費、サポート負荷と支払い意思を照合 |

有料化は利用上限・更新頻度・保持期間を定めた追加プランから評価する。料金、決済事業者、契約条件は未決定。決済導入前に商用データ利用・削除・解約時の扱いを確認し、購入者向け機能として別スコープで実装する。

独立アプリへの切り出しは、在庫連携を使わない別顧客層、法人API需要、独立リリース/負荷対策の必要性が実測で明らかになった場合に再評価する。共有DBへの恒久的な相互直接参照は避け、移行対象、所有者ID、認証、API互換、並行稼働/戻し方と二重運用費を計画する。

日付の約束は置かない。X0終了時に取得条件と試験データ、X1終了時に変更対象と受入例からX2/X3の工数を見積もる。API申請待ちと開発工数を分け、各段階を実装・検証・文書更新までの小さな単位に分割する。
